\begin{abstract}
Coding agents make plausible repairs cheap.  Teams still need a durable way to carry domain
corrections into future runs.  A correction should leave more than a passing test or a chat
note: it should name the rejected repair, the rule that rejects it, and the code or prompt
surface that must preserve it.

We use the term \emph{counterexample-supplemented sketch} for the repository artifact and
\emph{agentic synthesis} for the loop that edits against it.  A human writes a partial
program-like sketch.  A finite corpus stores observations and promoted counterexamples.
Subject-matter experts correct concrete outputs.  A coding agent edits deterministic code and
prompt surfaces under known-code anchors.  A gate blocks completion until replay and semantic
comparison pass for every promoted case.

The loop borrows from sketching and counterexample-guided inductive synthesis (CEGIS), but the
execution surface is different.  Classical sketching and CEGIS can make formal claims when the
search space, specification, and checker are formal.  Here, the synthesizer is an IDE-shaped
coding agent whose edits span ordinary source code and LLM prompt surfaces.  The claim stays
bounded: when the gate passes, the current strategy satisfies the repository's encoded replay
and comparison predicates for the promoted corpus.

The originating deployment ran inside a proprietary enterprise harness: a custom Cursor
extension, \texttt{cursor://}-style commands, and an embedded web application where
subject-matter experts loaded production examples, corrected outputs, and helped turn those
corrections into input/output specifications.  The public companion repository provides the
sanitized RosterSynth slice: the sketch, fixtures, code, tests, and generated evidence needed
to inspect the disclosed loop.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Coding agents change the cost of repair.  A developer can ask for a patch before the team has
encoded every domain rule the patch must respect.  The agent then optimizes against the signal
it can execute: a failing test, a state delta, a prompt instruction, or a reviewer note.  If the
rule behind a rejected repair stays in conversation, the next agent run can make the same
plausible mistake.

A rejected output should become a repository constraint.  The repository should capture the
input/output case, the rejected repair, the sketch clause that changed, and the replay/compare
gate that protects the rule.

Tests still matter.  They catch shape errors, exceptions, bad deltas, and regressions.  Prompts
can explain intent for the current run.  A promoted case has a different job: keep the
correction available to later agents under repository checks.

That path has these ingredients:

\begin{enumerate}[leftmargin=*]
  \item a \textbf{sketch} $\sketch$: a partial program in prose and code-shaped structure;
  \item a \textbf{counterexample-supplemented corpus} $\corpus$: examples, observations, and
        promoted failures;
  \item \textbf{known-code anchors} $\anchors$: codebase-local shapes, APIs, conventions, and
        reference paths the agent must preserve;
  \item a \textbf{dual-oracle implementation surface}: deterministic code for encodable holes
        and prompt-mediated completion for narrative holes;
  \item a \textbf{gate} $\gate$: replay plus semantic comparison over every promoted case.
\end{enumerate}

\begin{center}
\setlength{\fboxsep}{6pt}
\fbox{%
\begin{tabular}{c}
\textbf{Method at a glance} \\
\midrule
Human sketch $\sketch$ names strategy and holes \\
$\Downarrow$ \\

$\Downarrow$ \\
Replay checks state repair over each promoted case \\
$\Downarrow$ \\

$\Downarrow$ \\

\end{tabular}}

{\small\emph{The loop turns a tempting wrong repair into durable repository guidance.}}
\end{center}

The sketch records the human's current strategy: which repairs are permitted, prioritized, or
forbidden.  The corpus records cases that have earned specification authority through
promotion.  The gate is the executable boundary for the current done state.  A failure becomes
valuable when it changes the sketch and the corpus so future agent passes inherit the rule
instead of rediscovering the same local trap.

\paragraph{Central claim.}
A workflow is inspectable when every promoted counterexample connects four things: the sketch
clause it supplements, the implementation or prompt surface that handles it, the replay check
that verifies state repair, and the semantic compare check that rejects the tempting wrong
repair.  That gives maintainers a bounded gate invariant for the current promoted corpus and a
promotion procedure for new failures.

\paragraph{Positioning.}
The comparison target is bounded.  Existing agentic workflows can make tests and prompts
durable.  Classical CEGIS already has counterexample discipline when its formal assumptions
hold.  The repository setting here is smaller and messier: the human strategy, the promoted
counterexample, and the executable check often live in separate artifacts.  The work is to join
them without pretending the result is a solver-backed proof.

\paragraph{Contributions.}
The contribution is a formulation plus a worked artifact.

\begin{enumerate}[leftmargin=*]
  \item a repository-native artifact: the counterexample-supplemented sketch;
  \item a process model that turns subject-matter expert corrections into input/output specs,
        counterexamples, and golden data;
  \item two hole-filling roles: Oracle~A, deterministic code the agent maintains, and
        Oracle~B, prompt-mediated completion for sketch-declared narrative holes;
  \item a finite-corpus theorem for replay/compare gates and the proof obligation it leaves
        behind;
  \item a sketch-level RosterSynth example and companion repository for runnable inspection.
\end{enumerate}

The rest of the paper keeps that inspection path visible.  Section~\ref{sec:originating-setting}
describes the setting that forced the problem and the harness we built.  Section~\ref{sec:problem}
names the failure.  The lineage, artifact, role, lifecycle, and gate sections explain how a
promoted case moves from SME correction into sketch, code or prompt, replay, and compare.

\section{Originating setting}
\label{sec:originating-setting}

The enterprise deployment was the proving ground.  Production failures could be loaded into a
review surface.  SMEs corrected concrete outputs.  Agents repaired code and prompts.  CEGIS
gave us the loop for making failures reusable; this version adapts it to agentic repair: load
true failures from production, promote them into a golden set, and rerun the harness for each
new scenario.

The deployed system had eight pieces:

\begin{enumerate}[leftmargin=*]
  \item a custom Cursor extension for invoking repository actions from the IDE;
  \item \texttt{cursor://}-style URL commands connecting review actions to local agent
        workflows;
  \item an embedded web application where SMEs loaded production examples, inspected
        proposed remediations, and supplied corrections;
  \item an execution runtime: AWS Lambda invoked through SQS, with model calls through the
        Bedrock Converse API;
  \item a harness and test framework for fixtures, replay, semantic compare, golden corpus
        promotion, and provenance;
  \item LLM-assisted conversion from SME corrections into input/output specifications;
  \item a counterexample loop that promoted selected failures into a golden dataset;
  \item non-developer operation of the loop for code and prompt implementations of a complex
        data-cleansing pipeline.
\end{enumerate}

Lower formality was acceptable because the check stayed close to the people and artifacts that
could verify it.  SMEs inspected concrete outputs.  The harness replayed each promoted
scenario.  The golden set made regressions visible.  A correction was more than feedback on one
row; it was a candidate specification change with a path into the repository.

The public artifact is a real but not real-world example for illustration.  It keeps the shape
of the work without exposing production data or client rules: a paper, fixtures, tests,
provenance, and a small roster remediation case.  The reusable loop is:

\begin{center}
\begin{tabular}{c}
SME correction $\rightarrow$ input/output spec $\rightarrow$ promoted counterexample \\
$\rightarrow$ sketch update $\rightarrow$ agent repair $\rightarrow$ replay/compare gate
\end{tabular}
\end{center}

The RosterSynth case gives readers a concrete artifact for inspecting how the method represents
policy, encodes a promoted counterexample, and checks a repaired strategy.

\section{Problem}
\label{sec:problem}

Coding agents alter the economics of software change.  They reduce the cost of producing a
candidate patch.  They also increase the number of candidate patches that look acceptable
under incomplete specifications.  That combination makes the specification boundary more
important than the synthesis engine.  Cheap patch generation helps only when the surrounding
artifacts say which patch should be generated.

The sequence is recognizable:

\begin{enumerate}[leftmargin=*]
  \item A user gives an agent a domain task.
  \item The prompt names the obvious state gap.
  \item The agent finds a local patch that closes the visible gap.
  \item A subject-matter expert recognizes a policy violation.
  \item The violation was present in the domain, yet absent from the checkable artifacts.
\end{enumerate}

The patch can be technically clean.  The agent can follow local style.  The tests can pass.
The missing piece is the promoted counterexample: the artifact that says, ``this plausible
repair is forbidden for this reason, and future repairs must satisfy this rule.''  Without that
artifact, the team has learned something in conversation while leaving the repository nearly
unchanged.

\subsection{Tests need the rule they protect}

A test checks behavior.  A promoted counterexample records the rule behind the expected output.
That matters when two repairs close the same state delta.  Replay can show that a row fixes the
arithmetic.  Semantic compare can show whether it used the required operation, target, date, or
status.  The sketch explains why those fields matter.

Policy-heavy repairs fail when the test says what output to expect but not which rule the
repair must preserve.  A counterexample-supplemented sketch gives the rule a name, links it to
the fixture that exposed it, and tells the next repair which tempting path to avoid.

When the test is detached from the rule, a future maintainer or agent may patch around the
failing assertion.  A sketch clause linked to the test records the policy ordering a later
repair should preserve.

\subsection{Prompts need repository anchoring}

Run-local prompts can carry ambiguous intent in a way formal checks often cannot.  They can
state business rules, narrative criteria, exception handling, and domain language.  That
strength becomes fragile when the prompt lives in a chat transcript, notebook, model call, or
agent session outside the repository's review path.

The method still uses prompts.  It treats them as one implementation surface.  Oracle~B is
prompt-mediated completion constrained by the same sketch and corpus as deterministic code.
Prompt text can encode narrative criteria; the resulting output remains subject to the same
gate.  The repository becomes the place where the prompt, the fixture, the sketch clause, and
the check meet.

\subsection{A repository-native version of the loop}

Formal synthesis and CEGIS already cover a large design space.  When the template,
specification, and checker fit inside a formal language, a solver can search a constrained
space and return a result with more semantic force than the repository gate used here.
Counterexamples may come from a verifier, examples may guide inductive search, and oracles may
steer component selection or specification refinement~\cite{solar2006combinatorial,jha2010oracle}.

The repository setting buys a different kind of evidence.  Lower formality is acceptable when
the rule can be checked by SMEs against a sketch and promoted counterexamples.  Enterprise
data-cleaning is one of several settings where this technique has promise: the common condition
is SME-verifiable behavior before fully formalized rules.  Some rules become deterministic
code.  Others stay in prompts while the team gathers enough counterexamples to encode them.
Oracle~B gets the same validation: prompt-mediated output is replayed and compared against the
same promoted expectations.

This is a weaker result than formal synthesis.  The trade is SME-verifiable evidence: sketch
clauses, corrected examples, prompts, code anchors, checker fields, and generated provenance
all point back to the rule the last tempting repair violated.

\section{Lineage}
\label{sec:lineage}

\subsection{Sketch and CEGIS}

Solar-Lezama's sketching work framed synthesis as collaboration between programmer insight
and automated search: the programmer writes a partial program, leaving holes for a
synthesizer to fill~\cite{solar2008sketching,solar2013sketching}.  Earlier sketching work
already used counterexamples to refine candidates in finite-program synthesis
settings~\cite{solar2006combinatorial}.  The programmer supplies structure; the machine
searches within it.  CEGIS adds the validation loop: generate a candidate, validate it
externally, and feed counterexamples back into the next synthesis step.

That loop carries an important discipline.  A counterexample is more than a failing test case.
It removes a region of the candidate space by showing a concrete input on which the current
candidate violates the specification.  In solver-backed settings, the synthesizer can use the
growing counterexample set to search a formal space more intelligently than blind generate and
check.  Oracle-guided synthesis extends the picture by letting an oracle guide or validate
choices in component-based synthesis~\cite{jha2010oracle}.

\subsection{Programming by example}

Programming-by-example systems such as FlashMeta and PROSE synthesize DSL programs from
examples using domain-specific deduction~\cite{polozov2015flashmeta,gulwani2017program}.
Those systems show a different but related lesson: examples can be a specification surface
when the target language and domain-specific operators are chosen carefully.  The examples
serve as constraints on a search procedure inside a language designed for that family of
tasks.

\subsection{Agentic coding and tests}

Agentic coding work changes the repair surface again.  Agent benchmarks such as SWE-bench
evaluate whether language models can resolve real repository issues~\cite{jimenez2024swebench}.
Tests-as-prompts work studies tests as both input and evaluation for LLM code
generation~\cite{cui2025tests}.  These approaches already use repository artifacts and
executable checks to steer agents.  The method here is compatible with that direction.  It
adds a specific artifact boundary for policy-heavy repairs: every promoted counterexample
should say which sketch clause changed, which tempting repair is rejected, which code or prompt
surface handled the rule, and which gate check enforces it.

\subsection{Prompt engineering, specs, and natural-language coding}

Prompt programming and prompt-based learning treat natural-language prompts as a control
surface for language models~\cite{reynolds2021promptprogramming,liu2023pretrainpromptpredict}.
Language-Oriented Programming makes the software claim: natural language can lower the
barrier for non-experts who contribute to software projects~\cite{beheshti2024nlop}.
Promptware engineering then asks teams to treat prompts like software artifacts with
requirements, tests, debugging, evolution, and monitoring~\cite{chen2025promptware}.  Copilot
Workspace puts the same promise into product language: idea to code to software in natural
language~\cite{dohmke2024copilotworkspace}.  End-user software engineering is the older version
of the same concern: domain experts often create or maintain computational artifacts without
being professional software developers~\cite{ko2011enduser}.

Spec-driven agent tools make a related move.  Kiro uses requirements, design, and tasks to make
model assumptions visible before implementation~\cite{swaminathan2025kiro}.  GitHub Spec Kit
centers agentic development on a Spec--Plan--Tasks--Implement sequence and treats specs as
structured context for agents~\cite{github2026speckit}.  That is useful language, but
``spec'' can still hide too much.  Here, a spec means three things together: a sketch, promoted
counterexamples, and a replay/compare harness.  Specification by Example supplies the older
lesson: concrete examples become living documentation only when they are executable enough to
constrain future work~\cite{adzic2011specification}.

Prompt text belongs in the paper because it is one mutable implementation surface in the loop.
If a rule lives in a prompt today, the prompt needs the same pressure as
code: a sketch clause, promoted examples, replay, semantic compare, and an owner.  The sketch,
corpus, anchors, and gate keep that surface reviewable.

\subsection{Positioning boundary}

Agentic synthesis against counterexample-supplemented sketches borrows from several traditions
without treating any of them as a straw target.  The sketch resembles a partial program.  The
corpus resembles the growing example set in CEGIS and programming by example.  The gate
resembles a bounded validator.  The synthesizer is a coding agent with permission to edit source
and prompts.  The thing to inspect is the join among those artifacts.

The hole is shaped differently in an ordinary repository.  In classical Sketch, the hole is
usually inside a formal program and the solver searches a formal space.  Here, the hole can be
split across code, fixtures, prompts, review comments, and generated evidence.  A rule may need
one deterministic branch, one prompt instruction, one fixture, and one semantic compare field.
Counterexamples keep those pieces tied to the rule they are supposed to preserve.

\begin{center}
\scriptsize
\begin{tabular}{p{0.18\linewidth}p{0.22\linewidth}p{0.22\linewidth}p{0.27\linewidth}}
\toprule
 & Sketch / CEGIS & Programming by example & Repository loop \\
\midrule
Human input & Partial program with holes & Examples inside a DSL & Sketch, SME corrections, counterexamples, anchors \\
Synthesizer & Solver-backed search & DSL learner & Coding agent editing code and prompts \\
Failure signal & Counterexample from validator & Missing or inconsistent example & Gate failure or SME correction \\
Validation & Formal or bounded decision procedure & Example consistency & Replay plus semantic compare over $\corpus$ \\
Result boundary & Solver-relative result & DSL/example consistency & Finite-corpus predicate satisfaction under repo semantics \\
\bottomrule
\end{tabular}
\end{center}

Use the last column as a checklist for each promoted case: a sketch clause, a counterexample,
the edited code or prompt surface, and the gate check that fails the known bad repair.

\section{Artifacts}
\label{sec:artifacts}

The method assigns each artifact one job.  The sketch records strategy.  The corpus records
promoted cases.  Known-code anchors record local implementation shape.  The gate records the
current executable semantics.  Keeping those jobs separate makes failures easier to interpret:
when a gate fails, the maintainer can ask whether the sketch, corpus, anchor, implementation,
or checker needs to change.

\begin{table}[t]
\begin{center}
\small
\begin{tabular}{p{0.17\linewidth}p{0.34\linewidth}p{0.36\linewidth}}
\toprule
Artifact & Reader question & Failure if blurred \\
\midrule
Sketch & What rule should future repairs preserve? & The prompt drifts and the rule stays hidden. \\
Corpus & Which cases have specification authority? & Examples become anecdotes, not promoted constraints. \\
Anchors & What local code shape must the agent preserve? & The agent invents a second convention. \\
Implementation & Which code or prompt handles the hole? & A paper rule cannot be traced to the surface that applies it. \\
Gate & What behavior is executable now? & The claim floats above the repository instead of being checked. \\
\bottomrule
\end{tabular}
\end{center}
\caption{Artifact responsibilities from a reader's point of view.}
\label{tab:artifact-map}
\end{table}

\begin{definition}[Sketch]
A sketch $\sketch$ is a human-editable artifact that fixes the permitted strategy space and
names holes.  It may contain prose, tables, pseudo-code, type shapes, policy order, abstention
rules, and examples of forbidden repairs.  It persists in the repository and changes when a
counterexample reveals missing policy.
\end{definition}

A sketch should answer these questions for future maintainers and agent runs:

\begin{enumerate}[leftmargin=*]
  \item Which operations exist?
  \item Which operation has priority when several repairs close the same state gap?
  \item Which fields are policy-bearing?
  \item Which decisions belong in deterministic code?
  \item Which decisions belong in prompt-mediated narrative completion?
  \item Which cases force abstention or escalation?
\end{enumerate}

The sketch is deliberately less formal than a full specification.  Its job is to hold the
policy shape before every detail can be encoded.  That incompleteness is useful when the team
knows a rule exists but has not yet decided whether it belongs in code, prompt text, fixture
data, or human review.

\begin{definition}[Corpus]
The corpus $\corpus = \{(x_i, y_i)\}_{i=1}^{n}$ is the finite set of promoted examples the
current gate must satisfy.  Each input $x_i$ is a concrete scenario or fixture.  Each expected
output $y_i$ is the semantic repair the gate enforces.
\end{definition}

The corpus is authoritative because promotion is deliberate.  Raw examples can be noisy.  SME
corrections can contain ambiguity.  A promoted counterexample should meet an explicit
maintainer-reviewed threshold: it names a plausible wrong output, states the violated rule, and
is encoded in the gate.  Promotion turns a case from observed behavior into specification
pressure.

\begin{definition}[Known-code anchor]
A known-code anchor $\anchors$ is an existing source artifact that constrains the agent's
implementation style: an API, result type, parser convention, error shape, fixture format,
test helper, reference implementation, or prompt structure.  Anchors reduce the risk of
parallel local inventions.
\end{definition}

Anchors matter because agentic repair can accidentally create a second convention beside the
first.  A sketch names the policy.  Anchors name the shape the codebase already uses to carry
that policy.  They are especially important when an agent can satisfy a local test with a new
result shape that no downstream caller expects.

\begin{definition}[Gate]
A gate $\gate$ is the executable validation bundle that evaluates a candidate strategy
$\strategy$ over every promoted case in $\corpus$.  In this method the gate has two layers:
replay and semantic compare.
\end{definition}

Replay checks whether the proposed output changes the world state according to the encoded
state predicate.  Semantic compare checks whether the output used the encoded policy-bearing
fields from the promoted expectation.  The two layers separate state repair from policy
repair.  That separation matters because the most dangerous repair can be the one that makes
the arithmetic look right while choosing the wrong operation.

\section{Roles}
\label{sec:roles}

The method assigns distinct jobs to humans, agents, and checks.  The separation is practical.
SMEs know which output is acceptable.  Maintainers decide which corrections become
specification.  Agents repair implementation surfaces.  Gates report whether the current
strategy satisfies the encoded corpus.

\subsection{Subject-matter expert}

The SME supplies corrections on concrete examples through a review interface.  Their review
action says: this proposed output is wrong; the correct output is this; the reason is this
domain rule.  In the originating harness, the system helped convert that correction into an
input/output spec.  In the general method, the workflow needs some conversion path from SME
judgment to repository artifact.

The SME's correction has three parts:

\begin{enumerate}[leftmargin=*]
  \item the observed input;
  \item the corrected output;
  \item the explanation that distinguishes the corrected output from the tempting wrong one.
\end{enumerate}

The explanation matters because it seeds the sketch update and directs repair toward the
general rule the fixture exemplifies.  A corrected row alone can invite memorization.  A
corrected row plus a reason tells the next agent why the row matters.

\subsection{Developer or platform maintainer}

The developer supplies the rails: runtime, review UI, extraction path, fixtures, replay,
semantic compare, tests, and provenance.  In the originating harness, that meant Lambda invoked
through SQS, Bedrock Converse for model calls, repository-local commands, and gates that could
be run again after promotion.

The developer does not hand-author every domain rule.  SMEs and the harness control the rule
flow: corrections enter through the review interface, the harness turns them into candidate
specification artifacts, and promoted cases become part of $\corpus$.  Developer ownership is
over the machinery and anchors: whether the runtime runs, whether the gate checks the right
fields, whether the output shape stays compatible, and whether a promoted rule remains
inspectable.

\subsection{Coding agent}

The agent repairs the artifact under constraints.  It may edit deterministic code, prompt text,
fixtures, or tests.  Its job is synthesis inside the boundary set by $\sketch$, $\corpus$,
$\anchors$, and $\gate$.

The agent should receive three forms of context before editing:

\begin{enumerate}[leftmargin=*]
  \item the sketch clause involved;
  \item the counterexample and tempting wrong patch;
  \item the known-code anchors that define output shape and local conventions.
\end{enumerate}

That context changes the repair problem.  The agent is no longer asked only to make a failing
signal green.  It is asked to preserve a specific rule, reject a known tempting patch, and keep
the codebase's existing shape.

\subsection{Oracle A: deterministic code}

Oracle~A handles encodable policy.  It should be deterministic, reviewable source code:
grouping, filtering, ordering, type construction, deterministic abstention, and domain
calculations.  The agent can maintain it because the rule has been made concrete enough to
encode.

\subsection{Oracle B: prompt-mediated completion}

Oracle~B handles narrative or under-encoded policy: ambiguous notes, human descriptions,
client-specific language, or judgment that belongs in a model prompt for the current stage of
the system.  Oracle~B remains constrained by the sketch and checked by the same replay/compare
gate.  Its output is judged against the SME-approved corpus instead of treated as authority.

\subsection{Hybrid resolver}

A hybrid resolver tries Oracle~A first, then routes abstentions to Oracle~B.  This keeps
deterministic policy on the reliable path and leaves narrative completion explicit.  The split
also gives the team a migration path: a rule can begin in prompt-mediated completion, then move
into deterministic code once enough counterexamples make it precise.

\section{Counterexample lifecycle}
\label{sec:lifecycle}

The counterexample lifecycle is the core process.  It turns an observed failure into a
repository artifact the next agent must respect.  Each stage has a separate owner so the loop
keeps SME judgment, maintainer promotion, agent repair, and executable validation distinct.

\subsection{Observation}

A concrete case enters the review surface.  It can come from production data, a synthetic
fixture, a regression report, or a reviewer.  The system proposes an output.  The SME accepts
or corrects it.  At this stage the case is evidence, not yet specification.

\subsection{Correction}

A correction names the desired output and the rule behind it.  When possible, it also names the
tempting wrong repair.  That is where tacit domain knowledge becomes actionable: an expert says
which nearby output would have passed replay, and why policy still rejects it.

\subsection{Spec extraction}

The harness converts the correction into an input/output spec.  An LLM can help draft this
spec, especially when the SME explanation is prose.  The maintainer decides whether that draft
is precise enough to promote; the gate later enforces the encoded expectation.  This step is a
translation step, not an automatic source of truth.

\subsection{Promotion}

Promotion makes the case part of $\corpus$.  Promotion is a specification change.  The
promoted case must contain enough information to reject the tempting wrong repair.  A case
that only records the correct answer can still leave the rule ambiguous.

Promotion also creates maintenance work.  The sketch may need a new clause, the comparer may
need a new field, the fixture may need a clearer name, and the failure message may need to tell
the next agent where to look.  If those pieces are missing, the corpus grows without making
the repair problem clearer.

\subsection{Sketch revision}

The sketch changes with the corpus.  The revised sketch should state the general rule that the
counterexample exposed and the fixture answer that demonstrates it.  This protects the next
agent pass from memorizing one row.  The sketch is the place where the team names the rule;
the fixture is the place where the team records the concrete pressure that forced the rule into
view.

\subsection{Repair}

The agent repairs Oracle~A, Oracle~B, fixtures, or tests under the revised sketch.  Known-code
anchors constrain result shape and local convention.  The repair should close the promoted
case while preserving earlier promoted cases.  Otherwise the loop has only moved the failure.

\subsection{Gate}

The gate runs replay and semantic compare over all promoted cases.  A passing gate establishes
the Section~\ref{sec:correctness} result for the current strategy, corpus, checkers, fixtures,
and golden rows.  If any of those change, the gate must run again.

\section{Gate semantics}
\label{sec:gate-semantics}

The gate is the executable semantics of the current corpus.  It has two layers because state
repair and semantic repair fail differently.  Keeping those layers separate gives the next
agent a better error signal: a replay failure says the output failed the encoded state repair;
a compare failure says the output repaired state while violating an encoded policy field.

\begin{definition}[Replay]
Replay applies a candidate output $r$ to an input state $x$ and checks whether the proposed
change closes the domain gap.  Replay is domain-specific: it may compute balances, apply
updates, recalculate derived fields, or simulate downstream effects.
\end{definition}

\begin{definition}[Semantic compare]
Semantic compare checks fields that replay leaves open: operation kind, selected entity,
work date, issue type, status mutation, route, priority, or any other policy-bearing field
encoded by the comparer.  A row is compare-valid when it matches the promoted expectation on
those fields.
\end{definition}

\begin{definition}[Gate pass]
For a strategy $\strategy$ and corpus $\corpus$, the gate passes iff every
$(x_i, y_i) \in \corpus$ yields $r_i = \strategy(x_i)$ such that replay accepts $(x_i, r_i)$
and semantic compare accepts $(y_i, r_i)$.
\end{definition}

Replay is responsible for encoded state-repair failures.  Compare is responsible for encoded
policy-field violations.  A useful gate usually needs both because the two checks reject
different wrong repairs.  In the roster example, an append repair can close the hours math
while choosing the wrong operation; replay accepts the state change and compare rejects the
policy violation.

\subsection{Design rules for gates}

A gate should be deterministic, local, and specific.  It should run locally, report the exact
promoted case that failed, and preserve the difference between replay failure and compare
failure.  The failure message should tell the next agent which rule to inspect.

Good gates have these properties:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Promoted corpus coverage.}  Every promoted case runs.
  \item \textbf{Failure specificity.}  Replay and compare failures are reported separately.
  \item \textbf{Deterministic CI path.}  Gate-critical checks do not depend on a live model
        call.
  \item \textbf{Source links.}  Each failure can be traced to sketch clause, scenario, and check.
  \item \textbf{Tempting-patch rejection.}  The gate includes at least one check that fails the
        previously plausible wrong repair.
\end{enumerate}

These rules are design constraints rather than formal assurances.  A gate that omits a field
cannot enforce that field.  A comparer with a bug can certify the wrong behavior.  Gate design
is specification work, and checker quality belongs in the limitations rather than behind the
word correctness.

\section{Finite-corpus correctness}
\label{sec:correctness}

The proof obligation is intentionally bounded.  A passing gate establishes $\corpus$-
correctness relative to the current replay function, semantic comparer, fixtures, and golden
rows.  When a new failure is promoted into $\corpus$, it creates a larger proof
obligation; after the gate passes again, the same bounded result applies to the expanded
corpus.

\begin{definition}[$\corpus$-correctness]
A strategy $\strategy$ is $\corpus$-correct with respect to replay function $R$ and compare
predicate $C$ when, for every $(x_i, y_i) \in \corpus$,
$R(x_i, \strategy(x_i)) = \mathrm{true}$ and
$C(y_i, \strategy(x_i)) = \mathrm{true}$.
\end{definition}

\begin{lemma}[Replay soundness relative to the implementation]
If replay returns true for $(x, r)$, then $r$ satisfies the state-repair condition encoded by
replay for $x$.
\end{lemma}

\begin{proof}
Replay is the executable definition of state repair for the gate.  It evaluates the candidate
output against the input state and returns true exactly when the encoded state-repair predicate
holds.  A true replay result entails the state-repair condition the gate implements.
\end{proof}

\begin{lemma}[Compare soundness relative to the corpus]
If semantic compare returns true for expected output $y$ and candidate output $r$, then $r$
agrees with $y$ on every policy-bearing field encoded by the comparer.
\end{lemma}

\begin{proof}
The comparer enumerates the checked policy-bearing fields and fails on mismatch.  A true
compare result means every encoded policy-bearing field matched the promoted expectation.
\end{proof}

\begin{theorem}[Finite-corpus gate soundness]
If $\gate$ passes for strategy $\strategy$ on corpus $\corpus$, then $\strategy$ is
$\corpus$-correct with respect to the replay and compare semantics encoded by the
repository.
\end{theorem}

\begin{proof}
By definition, $\gate$ iterates over every $(x_i, y_i) \in \corpus$, computes
$r_i = \strategy(x_i)$, and requires replay and compare to pass.  By replay soundness, each
accepted $r_i$ satisfies the state-repair condition encoded by replay for $x_i$.  By compare
soundness, each accepted $r_i$ agrees with $y_i$ on every encoded policy-bearing field.
Thus every promoted corpus case satisfies both predicates, which is exactly
$\corpus$-correctness.
\end{proof}

\paragraph{Scope.}
The theorem covers the promoted corpus, the encoded replay checker, the encoded semantic
comparer, and the current golden rows.  It says nothing about unpromoted failures, unencoded
policy fields, future model behavior, or private deployment behavior outside the public
artifact.  Checker bugs require checker fixes.  Wrong golden rows require human correction.
The result is narrow enough to audit and strong enough to guide agentic repair: a maintainer
can see which predicate passed, which corpus it covered, and which boundary remains open.

\subsection{Scenario}

\section{Applying the method}
\label{sec:applying}

A lightweight version of the workflow can precede a full enterprise harness.  The practical
objective is to make every agent repair answer three questions: which rule is being used,
which example exposed it, and which gate would reject the tempting wrong repair.  Teams can
start with ordinary repository files and add automation only where the loop already works.

\subsection{Start with the sketch}

Write the intended strategy before asking the agent for code.  The sketch should name the
available operations, the priority order, the known holes, and the abstention cases.  Even an
incomplete sketch can be useful if it gives later failures a place to attach.  The first sketch
is a working surface, not a claim that the policy is complete.

\subsection{Collect examples before polishing code}

Examples are useful when they distinguish competing repairs.  A happy-path example shows
what success looks like.  A counterexample shows which plausible success should be rejected.
The second kind is especially useful for agentic repair because it teaches the boundary between
``green'' and ``right under this rule.''

\subsection{Name known-code anchors}

Point the agent at existing result types, parser behavior, fixture format, error shape, and
prompt conventions.  This reduces the chance that the agent creates a second local convention
just to satisfy the current case.  Anchors turn style and shape from tacit repository knowledge
into explicit repair context.

\subsection{Separate replay from compare}

Build replay and compare as separate checks.  A single assertion that says ``the output looks
right'' hides the distinction between state repair and policy repair.  Separate failures teach
the next agent more: replay failure means the state predicate stayed broken; compare failure
means the state predicate passed while a policy-bearing field diverged from the promoted
expectation.

\subsection{Promote failures deliberately}

Every failure should be triaged.  Some failures expose fixture bugs.  Some expose checker
bugs.  Some expose missing policy.  The last category belongs in $\corpus$ and $\sketch$.
Promotion is the moment where a case becomes part of the specification.

Deliberate promotion asks for more than a corrected answer.  It asks what tempting patch the
case rejects, which sketch clause should change, which field the comparer must check, and
which failure message will guide a future repair.  That extra work is the price of turning a
single failure into reusable specification pressure.

\section{Discussion}
\label{sec:discussion}

\subsection{Tests name behavior; sketches name intent}

Tests tell the current run what passed.  A sketch clause tells the next repair why the failure
mattered.  When a failing case joins $\corpus$, the sketch records the rule future agent passes
must preserve.  That is the useful temporal distinction: behavior now, intent next time.

\subsection{Prompts implement one surface of the contract}

Prompts handle narrative holes, ambiguous notes, and policy text that has not yet become code.
They are not outside the method.  The sketch and corpus constrain them, and the gate checks
their outputs.  In this loop, prompting is one implementation surface beside source code,
fixtures, and tests.

\subsection{SME corrections become specification inputs}

In the originating harness, SMEs corrected outputs through the review interface instead of
opening tickets for every specification change.  The harness turned those corrections into
candidate specs and counterexamples.  Maintainers still decided what entered $\corpus$.  The
SME contribution was the pressure: ``this output is wrong, and here is the domain rule it
missed.''

\subsection{Promotion quality is a scaling constraint}

A large pile of examples is weak guidance when the rule stays ambiguous.  A smaller corpus of
sharp counterexamples can be more useful because each case rejects a specific tempting patch.
The promotion question is concrete: what wrong repair would this case still allow if we left it
out?

\section{Limitations}
\label{sec:limitations}

\begin{enumerate}[leftmargin=*]
  \item \textbf{Finite corpus.}  The theorem covers $\corpus$.  New failures must be promoted
        and the gate must pass again before the bounded result covers them.  The method does
        not claim universal correctness across unseen cases.
  \item \textbf{Checker quality.}  Replay and compare inherit the limits of their encoded
        semantics.  A buggy checker can certify the wrong behavior until a maintainer repairs
        the checker and replays the promoted corpus.
  \item \textbf{Golden dataset quality.}  A wrong row in the golden dataset makes the gate
        enforce the wrong behavior.  Promotion needs review by someone who understands the
        domain rule and can distinguish a corrected answer from a corrected specification.
  \item \textbf{Promotion quality.}  A promoted case should distinguish a rule from a recorded
        answer.  Weak promotion gives future agents examples to memorize; strong promotion
        gives them rules to preserve.
  \item \textbf{Sketch quality.}  Hidden prose rules still require human review.  The method
        gives those rules a repository home, then relies on maintainers to keep that home
        current as new counterexamples arrive.
  \item \textbf{Prompt drift.}  Live model behavior can drift.  The method treats live output
        as something to review and promote, not as a stable proof artifact.
  \item \textbf{Enterprise evidence boundary.}  The public companion demonstrates the control
        structure on sanitized fixtures.  The proprietary harness motivates the method and
        remains outside the public artifact; the public evidence supports the loop and states
        the enterprise deployment boundary.
\end{enumerate}

The limitations are not cleanup after the method.  They mark where the proof stops and where a
person still owns the result: promotion, checker design, golden review, prompt review, and
private deployment claims.

\section{Conclusion}
\label{sec:conclusion}

A coding agent can write a patch.  This method asks for the trail that makes the patch
inspectable: the sketch clause, the promoted case, the code or prompt surface, the replay
check, and the semantic compare check.

The loop gives the agent a narrower job.  The human writes the sketch.  SMEs turn concrete
mistakes into promoted cases.  The agent repairs code or prompts under those cases.  The gate
then reports the exact boundary of the current repository: replay and semantic comparison pass
for the promoted corpus.

The enterprise setting supplied the pressure: SMEs knew the domain rule while agents controlled
the edit surface.  Each SME correction enters the repository as a promoted case.
Each promoted counterexample adds an executable check against a known wrong repair.  Each
passing gate states the bounded claim: the current strategy satisfies the encoded replay and
semantic-comparison predicates for the current promoted corpus.
