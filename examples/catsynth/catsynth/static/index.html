Agentic synthesis against counterexample-supplemented sketches

Coding agents fail when a broad prompt hides a constraint the human already knows. This harness makes the constraint explicit: a sketch names the intended shape, counterexamples name the tempting wrong output, deterministic anchors keep results on-policy, and an adversarial gate proves the wrong repair fails.

Below is one synthetic case followed end-to-end through the loop. Each step links to the live tab that runs it — read top to bottom, then click through.

Illustrative data: breed attributes and policy rows are simplified fixtures for demonstrating the method, not pet-selection or medical advice.

Worked case · FR-1 An owner has allergies and wants a “big, fluffy, affectionate lap cat.” The tempting output is Persian — it fits every preference. In the synthetic policy table, the expected output is Siberian, the matching breed marked hypoallergenic=true. Watch the gate catch the difference.
  1. 1

    Evolved sketch (S) — carry the learned policy

    Sketch S

    The sketch is a partial solution shape, not full code: which operations the resolver may return (recommend / abstain / escalate), their priority order, which fields are policy-bearing, and the repairs it must not make. For FR-1 the load-bearing clause is “preference match never overrides a hard rule,” so a non-hypoallergenic breed is a forbidden repair for an allergic owner.

  2. 2

    Anchors (K) — bind the result to known code

    Anchors K

    Known-code anchors are the conventions the resolver must reuse instead of inventing: the Recommendation output shape {operation, breed, cited_rules} and the local rule tables evaluated by one generic rule engine. A forbid rule removes a breed (hard); a discourage rule only penalizes it in ranking (soft). FR-1's hard rule is allergy_requires_hypoallergenic.

  3. 3

    Resolve — the coding-agent flow fills the holes

    Oracles A/B

    The resolver executes the sketch's holes: Oracle A (deterministic code) applies the hard/soft rules and ranks by preference; Oracle B turns a free-text note into soft constraints only and can never relax a hard rule. Toggle policy vs naive: policy obeys the rules and returns Siberian; naive ignores them and returns the tempting Persian — the wrong implementation the loop exists to catch.

  4. 4

    Operator approval → CE archive (A) — change the sketch

    Archive A

    A proposed counterexample names a plausible wrong implementation and becomes authoritative only when an operator explicitly approves it. Every accepted CE must change the evolved sketch. The archive preserves why; a curated regression set checks generated code. This small demo uses the same seeded cases for both roles (R = A). The Review button records only a local operator decision; it does not invoke Developer or edit repository files.

  5. 5

    Verify — the gate must fail the tempting patch

    Gate G

    Verification is adversarial: a useful check passes the intended behavior and fails the tempting wrong patch. The gate runs two checks over regression set R — replay (did we close the owner's state gap?) and approved-output compare (do the policy-bearing fields match?). Run it in naive mode and watch replay accept Persian while compare rejects it on the breed field.

  6. 6

    Review — compare simulated output with the sketch

    Sketch review

    After the deterministic gate passes, run the active case and regression set in simulation. A capable model or person compares each output with the current sketch. The captured experiment predates this required review record; use the Review tab to inspect the concrete policy and tempting outputs.

The lesson in one line

A state-valid repair can still be a policy violation. Run the deterministic gate, then review the simulated output against the sketch. Do not reveal another case until both pass.
